# Lab 38 - Observability

## Why this exists

Every earlier lab in this curriculum has assumed you can already SEE what a
database or a process is doing - `pino` logs printed to a terminal, an
`EXPLAIN ANALYZE` you ran by hand, a `pg_stat_activity` query you typed
yourself while something was blocked. That is fine for a lab you are
actively driving. It falls apart the moment you are not the one who
triggered the problem - an on-call engineer paged at 3am for "the API is
slow" has none of that context, only whatever the system already recorded
about itself before the page fired.

This lab is about building that recording, for real, and then using it to
actually diagnose a real incident this lab injects on purpose. The three
observability pillars - logs, metrics, traces - are usually taught as
separate slide bullets. Here they are one small real HTTP service with one
real bug, and the lab's entire "Break it"/"Fix it" arc is running that
service under realistic mixed traffic and then using logs, metrics, a
correlation ID, and `packages/db-utils/sql`'s own PostgreSQL inspection
scripts TOGETHER to find and explain a real failure - not four separate,
disconnected demos.

## Learning objectives

After this lab you should be able to:

- explain, with a real side-by-side comparison, why structured (JSON)
  logging with consistent fields is queryable/aggregable in a way
  free-text `console.log` calls are not, and quantify exactly how much of a
  real log file a naive parser silently fails to recover;
- instrument a real HTTP service with the four metric types that matter
  most operationally (request counter, latency histogram, in-flight gauge,
  error counter) plus real `pg.Pool` queue-depth gauges, and scrape a real
  `/metrics` endpoint - by hand and via a real Prometheus container;
- explain what a correlation/request ID actually buys you, demonstrated by
  firing concurrent requests, interleaving their log lines for real, and
  recovering one request's exact path by filtering on its ID alone;
- reuse `packages/db-utils/sql`'s shared PostgreSQL inspection scripts
  against REAL concurrent activity (a real blocked writer, a real
  long-running transaction) generated by this lab, not a canned example;
- walk a real, connected incident end to end: structured logs to find WHICH
  requests are the problem, a correlation ID to trace WHAT one of them did,
  metrics to tell whether it is systemic or a fluke, and Postgres inspection
  to determine whether the database is a contributing cause.

### Domain: a small standalone `orders` lookup service

`orders` (id, public_id, customer_email, amount_cents, status, created_at)
is a FRESH, standalone table - not Lab 03/04's commerce schema, not Lab
20's saga `orders`. This lab is about the observability TOOLING, not a rich
order domain, the same "small standalone table, the lesson is the
mechanism" rationale as Lab 06's `counters`/Lab 11's `documents`/Lab 31's
`page_views`. `customer_email` is nullable on purpose: ~5% of seeded rows
are real "guest checkout" orders with no email on file, and
`business-logic.ts`'s `buildOrderView` derives an email domain from it
WITHOUT a null check - a real, reproducible `TypeError`, not an injected
fake exception. That bug is this lab's entire "error" traffic bucket and
the incident the "Break it"/debug-narrative walk through.

### The service

Built on Node's own `http` module, deliberately not Express/Fastify - this
lab teaches instrumentation, not routing, and a bare `http.Server` keeps
every request-lifecycle step (where the correlation ID is minted, where a
timer starts, where a metric is recorded) visible in one file
(`src/server/server.ts`) instead of hidden inside framework middleware.

Routes: `GET /health`, `GET /metrics` (Prometheus text format), `GET
/orders/:id` (optional `?slow=1`), `POST /orders`.

Every request is traced through the same four steps ROADMAP.md's Lab 38
entry names - `request.start` (HTTP handler) -> `business_logic.*` ->
`db.query.*` -> `request.complete` (response) - logged through ONE
`requestId`-bound child logger and recorded into every metric this lab
exposes.

### Traffic mix (`src/scenarios/traffic-generator.ts`)

A deterministic, seeded (mulberry32) weighted mix, built from the actual
seeded data (valid ids vs. guest-checkout ids), not a hand-maintained list:

| bucket | weight | what it does |
|---|---|---|
| fast success | 65% | `GET /orders/:id` for a real, valid order |
| not found | 10% | `GET /orders/:id` for an id that genuinely does not exist |
| slow | 10% | `GET /orders/:id?slow=1` - a REAL `pg_sleep(0.3)` round trip first |
| error | 10% | `GET /orders/:id` for a real guest-checkout row - trips the real bug |
| create | 5% | `POST /orders` |

### Why `prom-client` (CLAUDE.md "Dependencies")

The Prometheus text exposition format has real rules that are easy to get
wrong by hand (label escaping, `# HELP`/`# TYPE` lines, histogram buckets
needing correct cumulative `_bucket{le=...}` counts plus `_sum`/`_count`).
Hand-rolling risks a `/metrics` endpoint that looks right in a terminal but
a real Prometheus server mis-parses - exactly the opposite of what an
observability lab should teach. `prom-client` is small, single-purpose, has
no framework dependencies, and is the de facto standard Node client for
this job. The lesson here is "what a real service instruments and how an
operator reads it," not "how the exposition format works internally," so a
correct, standard client is the more honest choice.

### Why a real Prometheus container, and no Grafana

CLAUDE.md's Technology Defaults explicitly allow "Prometheus/Grafana only
where observability is a learning objective" - this is that lab, so
`docker-compose.yml` includes a REAL `prom/prometheus` container that
scrapes this lab's own `pnpm dev` process every 5 seconds (see
`prometheus/prometheus.yml`; `host.docker.internal` + `extra_hosts:
host-gateway` makes this work on both Docker Desktop and native Linux
Docker, since this repo never containerizes a lab's own app process - only
its infrastructure dependencies). Grafana is deliberately NOT included:
it would only re-visualize the exact same `/metrics` data Prometheus
already scrapes and this README already shows numerically - no new
mechanism, only a dashboard-building exercise that is out of scope for the
core lesson (a scope/complexity tradeoff, not a claim that Grafana lacks
value in production). See "Further experiments" for how to add it yourself.

### Why the app's HTTP port is NOT `84NN`/`54NN`

This is the first lab to run its own in-process HTTP service, so
`ROADMAP.md`'s port-convention header now also documents: labs running an
app service of their own use host port `4NN` (`4438` here), and labs adding
Prometheus use `9NN` (`9438` here; Grafana would use `3NN` if a future lab
adds it). Postgres (`5438`) and PGweb (`8438`) keep the existing convention.

## Break it

### 1. Structured logs vs. naive free-text logs (`pnpm scenario:structured-logging`)

Real captured output, 300 real requests against the real service:

```text
=== REAL aggregates computed from structured.log (one JSON.parse per line + group-by) ===

/orders/:id  total=288  errorRate=9.7%  p50=1.86ms p95=308.84ms p99=311.24ms (min=0.42ms max=313.59ms)
/orders      total=12   errorRate=0.0%  p50=2.8ms p95=4.69ms p99=4.69ms (min=1.37ms max=4.69ms)

Overall: 300 completed requests, 28 errors, error rate 9.33%

=== Attempting the SAME aggregate from naive.log's free-text lines ===

naive.log: 300 total lines, 100 matched a single hand-written regex, 200 lines silently dropped from
the aggregate (different format, or an ERROR line with no duration), 100 of the matched lines had NO
way to express outcome so were implicitly treated as success.
```

The structured aggregate is EXACT: every one of the 300 requests is
accounted for, by route, by outcome, with real p50/p95/p99 latency. The
naive aggregate recovers at most **100 of 300 lines (33%)** with a single
reasonable regex - not because the regex is bad, but because
`appendNaiveLogLine` deliberately writes THREE different free-text formats
for the same event (exactly how three different engineers' `console.log`
calls diverge over a codebase's lifetime), and error lines carry no
duration field at all. The 100 lines it DOES match have no way to express
outcome (success/not_found/error) either - the free-text format never
named that field, so a naive parser would have to GUESS.

## Fix it

The "fix" here is the diagnosis method itself, already demonstrated above -
but the underlying bug (`business-logic.ts`'s unguarded
`order.customerEmail!.split("@")`) has a real one-line fix:

```ts
const emailDomain = order.customerEmail?.split("@")[1]?.toLowerCase() ?? "unknown";
```

This was verified for real during this lab's own validation - applying the
one-line change above and re-running `pnpm scenario:debug-narrative`
produced `/orders/:id: 288 requests, 0 errors (0.0%), ...` (down from 28),
and the script's OWN "pick a sample error to investigate" step correctly
found none left to pick. Re-running `pnpm test` with the fix applied,
however, FAILS on purpose: `structured-logging.test.ts` asserts
`ordersAgg.errorCount` equals `mix.error` (the traffic generator's own count
of how many guest-checkout requests it sent, i.e. a real, non-zero number)
- a real, deliberate invariant that the error bucket's requests really do
error. The fix was reverted after validation, on purpose: this lab's error
bucket, its tests, and every captured number in this README all depend on
the bug being genuinely present in the shipped lab, the same reason Lab 10's
naive withdrawal code and Lab 12's naive reservation code stay in their
repos permanently rather than being replaced by their own corrected
version - the "before" state is part of what the lab teaches, not a
scratch draft. Apply the one-line fix yourself (see "Further experiments")
to reproduce this section's result firsthand.

## Why the fix works

- **Structured logging works because every field is NAMED and TYPED**, not
  because JSON is inherently better than English. `route`, `durationMs`,
  `outcome`, `requestId` are the same four facts an operator needs from
  every single request, in the same place, every time - so `JSON.parse` +
  `group by` is all an aggregation needs. Free text has no such contract;
  every log CALL SITE is free to invent its own shape, and different call
  sites did, in this lab's own `appendNaiveLogLine`.
- **A correlation ID works because it is the one field EVERY log line for
  one request shares**, regardless of which process, which async step, or
  which other request's lines happen to interleave with it at the exact
  same millisecond. Filtering is just `WHERE requestId = X` - no timing
  assumptions required.
- **Metrics work because they are pre-aggregated at write time.** A
  Counter/Histogram never needs to re-scan raw events to answer "how many"
  or "how slow, at what percentile" - `prom-client` maintains the bucket
  counts incrementally, which is why a `/metrics` scrape is O(1) relative
  to total traffic volume, unlike log aggregation.
- **Postgres inspection works because `pg_stat_activity`/`pg_locks` are the
  database's own, always-current account of what it is doing right now** -
  no instrumentation had to be added to the application for these to be
  accurate; they exist for every PostgreSQL database, including ones you do
  not control the code of.

## Tradeoffs

- **Structured logging costs more bytes per line** (field names repeated
  every line) and needs log-processing tooling to pay off at scale - for a
  handful of requests a human can just read either format. The payoff is
  entirely in AGGREGATE queries across many requests, which is exactly the
  scale at which free text stops working.
- **A correlation ID is only as good as its PROPAGATION.** This lab's
  service is a single process, so propagation is "pass the same string to
  every log call" - a real multi-service system needs to forward the same
  ID across HTTP calls, queue messages, and worker processes (ROADMAP.md's
  own "API -> database -> outbox -> publisher -> consumer" trace), and any
  hop that drops it breaks the whole chain.
- **Prometheus's pull model means a target that is down between scrapes is
  invisible until the next scrape** - `scrape_interval: 5s` here is a lab
  convenience; a real incident that starts and resolves faster than the
  scrape interval can be entirely missed by metrics alone, which is why
  logs and traces still matter even with good metrics.
- **This lab's percentile computation
  (`src/observability/percentiles.ts`) sorts and ranks raw samples in
  memory** - exact at this lab's scale (hundreds of requests), but that
  does not scale to production request volumes; `prom-client`'s own
  Histogram (bucketed, not raw-sample) is the production-appropriate
  approach and is what this lab's `/metrics` endpoint actually exposes for
  real dashboards - the raw-sample percentile helper exists here purely to
  make the "why structured logs let you compute this at all" point
  concretely, not as the production technique.
- **Route TEMPLATES (`/orders/:id`), not raw paths, are used as metric
  labels** - a real, easy-to-get-wrong cardinality trap: labeling metrics
  by raw path (`/orders/1`, `/orders/2`, ...) would create one time series
  PER ORDER ID, growing without bound and eventually overwhelming
  Prometheus. This lab's `server.ts` deliberately templates the route
  before it ever reaches a metric label.

## Production notes

1. **What guarantee does this mechanism give?** Structured logs +
   correlation IDs + metrics + Postgres system views together give an
   operator a REPRODUCIBLE, QUERYABLE record of what a service and its
   database did, without needing to have been watching in real time.
2. **What guarantee does it NOT give?** None of this prevents the
   underlying bug (a missing null check is still a missing null check) -
   observability makes a problem fast to FIND and CHARACTERIZE, not fast to
   avoid writing in the first place.
3. **What failure mode remains?** A correlation ID that is not propagated
   across a process boundary (a queue message, an outbox event, a
   downstream HTTP call) silently breaks the trace at exactly that hop -
   the operator sees the request "disappear" partway through with no error
   explaining why.
4. **How does contention affect it?** High log/metric volume itself
   becomes an operational cost (log storage, cardinality growth, scrape
   payload size) - this lab's own `/metrics` payload is already ~13KB at
   a few hundred requests' worth of label combinations; a route template
   that is NOT bounded (see the cardinality tradeoff above) grows this
   without limit.
5. **What changes at larger scale?** Raw-sample percentiles
   (`percentiles.ts`) stop being feasible; log aggregation moves to a
   dedicated platform (Loki/Elasticsearch/CloudWatch Insights) rather than
   `JSON.parse`-ing a single file; Prometheus itself needs remote-write/
   federation for retention beyond its local TSDB's practical window.
6. **What metrics would be monitored?** `http_errors_total` rate (by
   route), `http_request_duration_seconds` p95/p99 (by route),
   `http_requests_in_flight` (load), and `db_pool_waiting_clients` (a real
   queue-depth signal - a sustained non-zero value means the application
   is bottlenecked on database connections, not the database itself).
7. **When should this approach be avoided?** Never, for a service with
   any production traffic - the question is really "how much" (sampling
   rate for traces, retention for logs, cardinality budget for metrics),
   not "whether."

## Interview questions

1. Why does a single hand-written regex recover only a third of this lab's
   own `naive.log`, even though every line describes a real, successfully
   handled (or failed) request?
2. `http_requests_in_flight` reads `1` immediately after a request
   completes, in a service with zero other concurrent traffic. Why - and
   why is `0` actually the WRONG expectation for that specific moment?
3. Why must a correlation ID be generated (or forwarded) BEFORE any
   business logic runs, rather than only being attached to the final
   `request.complete` log line?
4. Why does labeling `http_requests_total` by raw path (`/orders/1`,
   `/orders/2`, ...) rather than a route template become a production
   incident of its own, independent of the original bug being measured?
5. Given `pg_stat_activity` shows 5 backends running `pg_sleep`-backed
   queries during a slow-request burst, but 0 non-idle backends during an
   error-request burst, what can you conclude about where each problem's
   root cause lives - and what would change your conclusion?
6. Why is a Prometheus Histogram's bucket-based approach preferred at
   production scale over this lab's own raw-sample percentile helper, even
   though the raw-sample version is more precise at this lab's own scale?
