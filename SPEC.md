# Backend Engineering Systems Labs — SPEC.md

## 1. Mission

Build a hands-on, production-oriented backend engineering curriculum as a single repository of independent labs.

The goal is not to teach backend engineering from scratch. The goal is to create a deliberate-practice environment for an experienced engineer to rehearse, observe, break, and deeply understand important backend and distributed-systems concepts.

The repository should make it easy to:

- run a lab locally with minimal setup;
- reproduce race conditions and failure modes;
- inspect PostgreSQL state visually through PGweb;
- see the SQL generated by Drizzle;
- compare ORM code with raw SQL;
- generate realistic deterministic data;
- observe locks, transactions, replication, queues, retries, and migrations;
- understand both the happy path and failure path;
- connect each implementation to production system-design tradeoffs;
- use the repository as both a study environment and a portfolio artifact.

The primary learning method is **lab-driven deliberate practice**:
1. predict what should happen;
2. run the experiment;
3. observe what actually happens;
4. explain why;
5. change one variable;
6. rerun;
7. document the tradeoff.

---

## 2. Audience

This repository is designed for an experienced backend engineer who already understands application development and wants to sharpen systems knowledge through implementation.

The labs should therefore:

- avoid overly basic programming instruction;
- explain database and distributed-systems concepts precisely;
- expose implementation details instead of hiding everything behind abstractions;
- use realistic schemas and scenarios;
- include production caveats and scaling considerations;
- encourage direct inspection of PostgreSQL behavior.

## 4. Repository Principles

### 4.1 Every lab is independent

Each lab must be runnable in isolation.

A lab must not require another lab's database, Docker network, migrations, or running process.

Each lab owns:

- its own `docker-compose.yml`;
- its own `.env.example`;
- its own schema;
- its own migrations;
- its own seed data;
- its own scripts;
- its own README;
- its own tests.

Shared packages may provide utilities, but no lab should require another lab directory.

### 4.2 Prefer observation over explanation

Every major concept must be demonstrated through behavior.

Examples:

- a race condition should actually occur before it is fixed;
- replication lag should actually be observable;
- a blocked transaction should actually wait;
- `SKIP LOCKED` should visibly distribute jobs across workers;
- a serialization failure should actually be produced;
- an unsafe migration should visibly block or fail before the safe version is introduced.

### 4.3 Show the failure first

Where practical, labs should follow:

1. naive implementation;
2. reproduce failure;
3. inspect why;
4. implement correction;
5. compare guarantees and tradeoffs.

### 4.4 Keep guarantees close to the data

Labs should emphasize a recurring systems principle:

> If a correctness invariant belongs to the datastore, prefer enforcing it in the datastore rather than coordinating application instances unnecessarily.

This principle should surface repeatedly in:

- uniqueness constraints;
- conditional writes;
- transactions;
- row locks;
- isolation levels;
- advisory locks;
- idempotency;
- outbox processing.

### 4.5 ORM plus SQL

Drizzle is the main ORM, but the labs must not hide PostgreSQL.

Use raw SQL where:

- PostgreSQL exposes functionality more naturally than the ORM;
- the SQL is central to the concept;
- lock behavior needs to be explicit;
- query plans need to be inspected;
- a PostgreSQL-specific feature is being taught.

Whenever practical, include both:

- the Drizzle implementation;
- the equivalent SQL.

## 7. Standard Lab README Format

Every lab README must contain:

### Title

Clear name of the concept.

### Why this exists

A production problem that motivates the concept.

### Learning objectives

What the learner should understand after completing the lab.

### Architecture

A short description or Mermaid diagram.

### Setup

Exact commands.

Example:

```bash
pnpm install
cp .env.example .env
docker compose up -d
pnpm db:migrate
pnpm seed
```

### Scenario

Describe the domain problem.

### Prediction

Ask the learner to predict behavior before executing the experiment.

### Exercise

Steps to implement or run.

### Observe

Explicit things to inspect:

- SQL logs;
- PGweb;
- process output;
- `pg_stat_activity`;
- `pg_locks`;
- row state;
- timestamps;
- query plans;
- lag metrics.

### Break it

A controlled failure experiment.

### Fix it

Implement the production-safe version.

### Why the fix works

Explain the invariant being protected.

### Tradeoffs

Performance, complexity, consistency, failure recovery.

### Production notes

How the technique changes in a large production environment.

### Interview questions

Three to eight design questions relevant to the lab.

### Further experiments

Ideas for modifying timing, worker count, dataset size, isolation level, failure timing, topology, or retry behavior.

## 8. Data Generation Strategy

The repository must avoid meaningless random records.

### 8.1 Deterministic data

Every seed generator must accept a seed.

Example:

```bash
pnpm seed --seed=42
```

Running the same seed must produce the same logical dataset.

This is especially important for concurrency and performance labs.

### 8.2 Realistic domains

Use a small number of coherent domains throughout the curriculum.

#### Payroll

Entities:

- companies;
- employees;
- contracts;
- payroll periods;
- payroll runs;
- payslips;
- deductions;
- tax entries.

Useful for:

- advisory locks;
- transactions;
- idempotency;
- long-running jobs;
- batch processing;
- serializable transactions.

#### Ticketing

Entities:

- events;
- venues;
- sections;
- seats;
- ticket inventory;
- reservations;
- orders;
- payments.

Useful for:

- race conditions;
- conditional writes;
- row locks;
- optimistic concurrency;
- reservations;
- high contention;
- read-after-write.

#### Commerce

Entities:

- customers;
- products;
- inventory;
- carts;
- orders;
- order lines;
- payments;
- shipments.

Useful for:

- transactions;
- outbox;
- sagas;
- idempotency;
- inventory constraints.

#### Banking/Ledger

Entities:

- accounts;
- transfers;
- ledger entries.

Useful for:

- isolation anomalies;
- serializable;
- invariants;
- deadlocks;
- retries.

#### Background processing

Entities:

- jobs;
- attempts;
- workers;
- schedules.

Useful for:

- `FOR UPDATE SKIP LOCKED`;
- leases;
- retries;
- backpressure.

### 8.3 Faker

Prefer a deterministic faker library such as `@faker-js/faker`.

Generated data should respect domain constraints.

Bad:

```text
employee salary = random number from 1 to 1,000,000
```

Better:

- role determines salary band;
- country determines currency;
- employment start date precedes payroll period;
- manager belongs to same company;
- orders reference real products;
- ticket seats belong to the correct venue section.

### 8.4 Large datasets

Labs that require scale should provide commands such as:

```bash
pnpm seed --size=small
pnpm seed --size=medium
pnpm seed --size=large
pnpm seed --rows=1000000
```

Avoid committing huge generated data files.

Generate data locally.

# 17. Learning Philosophy

This curriculum must repeatedly reinforce the following distinctions.

### Coordination vs correctness

Distributed locks coordinate actors.

Database constraints and transactions protect data invariants.

Do not confuse them.

### Reservation vs locking

A reservation is a business state.

A lock is a concurrency mechanism.

A reservation system may use locks or conditional writes internally, but they are not the same concept.

### Cache vs source of truth

Redis may improve latency and throughput.

PostgreSQL remains authoritative for critical booking/payment invariants unless a lab intentionally explores another model.

### Retry vs idempotency

Retries improve availability.

Retries without idempotency can duplicate side effects.

### Replication vs consistency

Read replicas improve scalability and locality.

They introduce stale-read possibilities.

### ORM vs database

An ORM helps application development.

It does not replace understanding SQL, transactions, locks, indexes, execution plans, or database-specific features.
